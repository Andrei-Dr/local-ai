# Our patches on different hardware: 2x AMD MI210 (2026-09-24)

A friend's box (Dave) lent us both MI210s for one evening: AMD Instinct MI210 64 GB (gfx90a, HBM2e 1.6 TB/s), EPYC 74F3 24 cores,
512 GB DDR4 8-channel, PCIe 4.0, ROCm 7.1.4. Stock llama.cpp e613ef2 vs e613ef2 + our series 0001-0030 (tree 0f14b78, the STABLE
source), both built for HIP gfx90a. Scripts: `bench/dave/dave1.sh`, `bench/dave/dave2.sh` (rules pre-registered in their
headers). Raw rows: `bench/dave/results/`. temp 0, 300 generated tokens per prompt, 2 interleaved reps per arm (S4: 1).

## What it says
- The expert cache is tuned for a WEAK CPU. On the i5 a miss costs a 6-core AVX2 CPU on 38 GB/s DDR4, so a GPU hit is a big win.
  Dave's 24-core EPYC on 8-channel DDR4 computes Qwen's small experts fast enough that the cache's bookkeeping and uploads cost
  more than they save (S2). With DeepSeek-V4's much bigger experts the CPU side is slow again and the cache wins +40% (S3). The
  rule that transfers: the cache pays when the CPU expert phase is the critical link, not by default.
- Prefill mode (0011-0013, 0024-0030) transfers everywhere experts are offloaded: 2.1x (S2) and 1.8x (S3).
- When nothing is offloaded the series is neutral (S4) and the draft vocabulary is its only live lever (S1, +2.3%).
- Bug found and fixed: 0031. Prefill mode split long prompts at -ubp 2048 while create_memory sized every KV cache for -ub 128.
  A full-context cache does not care; DeepSeek-V4's sliding-window cache holds n_swa + one ubatch (256 cells), so the 2048-token
  ubatch found no slot (`find_slot: n_tokens = 1348 > size = 256`), the server retried smaller batches, and the GPU faulted
  (HSA_STATUS_ERROR_MEMORY_FAULT, exit 139). 0031 sizes window caches for max(n_ubatch, n_ubatch_prefill). Qwen3.6 has no window
  layers, so its allocation (and output) cannot change. dave2: all 8 runs completed, 0 find_slot errors (logs in results/runs/logs).
- Open: the smaller-batch retry path inside prefill mode faulted instead of failing cleanly; 0031 removes the trigger, the retry
  path itself is untested (a full KV cache in prefill mode would reach it).

## Round 2 (dave3 - dave5): Dave's build, the combo, vLLM, long prompts

Builds, all HIP gfx90a with Dave's CMake flags (`bench/dave/build_dave.sh`): **stock** (upstream, the image's toolchain),
**dave** (030ebb558 + his 11 MI210 patches = fork branch `dave/mi210`), **ours** (the STABLE series + 0031), **combo** (ours +
Dave's patches that apply, tree f8130ba = fork branch `dave-combo`; his 08 superseded upstream, 12 is a 2-GPU restore fix no arm
runs, 10 merged by hand). vLLM = Dave's image `local/vllm-mi210:rocm10-mi210.7-aiter-jitwarm` serving GPTQ-Int4 (a different
quantization than the llama.cpp arms' Q4_K_M: its speeds are not at equal accuracy). Scripts `bench/dave/dave3*.sh`, `dave4.sh`,
`dave5.sh`; raw logs in `bench/dave/results/`. t/s; "pf" = prompt tokens / time to first token; "after" = the 128 tokens after it.

Two kinds of comparison, never mixed:
- **engine vs engine**: identical flags except the build (dave3c, S3/S4, dave5).
- **each at its best**: ours with the draft model (MTP) and our batch sizes vs Dave's documented config (dave3 S1/S2, dave4).

### What round 2 says
- Dave's patches and ours stack: the combo was never worse than the better of the two beyond the spread, and wins S1 (at its
  best), S4 prefill, S3 decode, and every long resident prompt. The fork branch `dave-combo` is the build to hand Dave.
- On CDNA the prefill gap is his MFMA kernels plus batch size; nothing in them maps to the i5 (sm_75 without MMA; stream-k is
  already off there on every MMQ path, see the lead1 note).
- vLLM wins short-context decode with speculation; llama.cpp wins long prompts (prefill from 66k, decode at every depth without
  speculation). Equal-accuracy claims need the same weights, which these arms do not have.
